# Клиент купола v2

Рабочее подключение подтверждено 26 октября 2026 года в 16:16 (Москва): `wss://janus-server.a.2na.am:443/`, роль `team`, команда 1, 37 узлов, телеметрия поступает. Дополнительный локальный прокси отключён.

Python 3.11+. Общее ядро `dome_api.py` используется консолью `dome_client.py` и локальной панелью `dome_web.py`. Транспорт v2 — aiohttp; описание методов: https://docs.aiohttp.org/en/stable/client_reference.html#clientwebsocketresponse.

## Быстрый запуск

Подготовьте `.venv` и зависимости по инструкции установки ниже.

```powershell
.\.venv\Scripts\python.exe dome_web.py --url wss://janus-server.a.2na.am:443/
```

Панель: `http://127.0.0.1:8780/`. «Проверить один раз» выполняет одну попытку; «Подключить» включает наблюдение с переподключением. «Отключить» останавливает соединение и повторы. При запуске самой панели соединение ещё не устанавливается.

Разовая проверка из консоли:

```powershell
.\.venv\Scripts\python.exe dome_client.py --url wss://janus-server.a.2na.am:443/ --once
```

Диагностика с отдельными TCP/HTTP-пробами, затем WebSocket и проверкой API:

```powershell
.\.venv\Scripts\python.exe dome_client.py --url wss://janus-server.a.2na.am:443/ --diagnose
```

Постоянное наблюдение: убрать `--once`. Остановка — Ctrl+C. Панель и консоль используют один и тот же протокол и порядок восстановления соединения.

## Локальный туннель

Для локального SOCKS5 или HTTP CONNECT есть явный параметр `--proxy`:

```powershell
.\.venv\Scripts\python.exe dome_client.py --url wss://janus-server.a.2na.am:443/ --proxy socks5://127.0.0.1:10808 --once
.\.venv\Scripts\python.exe dome_client.py --url wss://janus-server.a.2na.am:443/ --proxy http://127.0.0.1:10809 --once
```

Постоянный маршрут задаётся как `DOME_PROXY=socks5://127.0.0.1:10808` в `.env`. Панель использует ту же настройку после перезапуска и показывает маршрут. Системные маршруты и настройки Happ не меняются. При недоступности прокси клиент не переключается на прямое соединение.

Это туннель через уже работающий локальный прокси. Для SSH-проброса через отдельный сервер потребуются адрес SSH-сервера и разрешённый способ входа. Если SSH-туннель уже поднят, клиенту можно указать его локальный WebSocket-адрес, например `ws://127.0.0.1:18765/ws`, без `DOME_PROXY`.

Повторная проверка старого адреса `62.118.24.234:48765/ws` 26 октября 2026 года: через локальные SOCKS5 `10808` и HTTP CONNECT `10809` WebSocket-рукопожатие также завершилось таймаутом. Успешное подключение к куполу через эти маршруты не подтверждено.

## Адрес и ключ

Сохраните свой ключ и адрес в локальном `.env`, который исключён из Git. Пример настройки:

```dotenv
DOME_URL=wss://janus-server.a.2na.am:443/
DOME_KEY=YOUR_TEAM_KEY
DOME_CONNECT_TIMEOUT=15
DOME_REQUEST_TIMEOUT=15
DOME_IDLE_TIMEOUT=20
DOME_PING_INTERVAL=30
DOME_RECONNECT_DELAY=5
DOME_WS_PATH=
AGENT_LOG_DIR=logs
```

Клиент принимает `ws://`, `wss://`, `http://` и `https://`. HTTP-адрес преобразуется в WebSocket на том же хосте и порту. Для известных страниц `/index.html` и `/static/index.html` выбирается корень `/`. Это преобразование **не доказывает**, что сервер обслуживает API именно по этому пути.

Если организаторы сообщили отдельный WebSocket-путь, укажите его прямо в адресе панели (`ws://HOST:PORT/ws`) или через `DOME_WS_PATH`. Для консоли есть явный параметр:

```powershell
.\.venv\Scripts\python.exe dome_client.py --url http://HOST:PORT/ --ws-path /ws --once
```

Порты и пути автоматически не перебираются. Ключ передаётся JSON-сообщением `auth` после успешного WebSocket-рукопожатия; в URL и HTTP-диагностику он не включается. Междоменное перенаправление отклоняется. TLS-сертификаты проверяются. Системные proxy-переменные не используются: без `DOME_PROXY` соединение прямое; с `DOME_PROXY` используется только явно заданный локальный туннель.

Переменные окружения имеют приоритет над `.env`, параметры командной строки — над окружением. Настройки таймаутов и задержек используются и консолью, и панелью.

## Что изменено в v2

- Отдельные этапы: TCP/TLS → WebSocket HTTP 101 → авторизация → API → телеметрия. Ошибка содержит этап, код и объяснение.
- При HTTP 200/404 вместо WebSocket клиент сообщает о неверном порте/пути. Такие ошибки и отказ авторизации не вызывают бесконечные повторы.
- Для сетевых сбоев используется растущая задержка с небольшим случайным смещением. Одновременно активна одна попытка.
- Один читатель распределяет ответы по `request_id` и типу сообщения; телеметрия и сообщения чата принимаются между ответами. Показания, пришедшие до `auth_response`, сохраняются.
- Отдельные таймауты соединения, авторизации/запросов и отсутствия телеметрии. Для активной команды замерший поток вызывает переподключение, даже если WebSocket остаётся открыт.
- Режим гостя проверяет авторизацию и ping; недоступная гостю телеметрия оборудования не считается ошибкой.
- Ограничение частоты запросов, очистка ожидающих ответов, закрытие соединений и отмена задач при остановке. Ошибка обработчика интерфейса не останавливает протокол.
- Ключи редактируются в журналах и ответах локальной панели. При сетевых ошибках ключ не выводится.

Консоль по умолчанию выполняет только чтение: `ping`, `describe_nodes`, `query`, телеметрия и входящий чат. Веб-панель поддерживает ручную отправку разрешённых команд (см. ниже). Это основа будущего управляющего агента, без DeepSeek и RAG.

## Управление в веб-панели

На карточке устройства нажмите «Управление и запросы», выберите команду, заполните параметры и нажмите «Выполнить команду». Перед отправкой показывается точный JSON. Список действий получен из текущего `describe_nodes`; физические действия из `operator_controls` не отправляются в API. Поля имеют диапазоны и типы из документации. Для станков есть проверки занятости, свободного стола и активных интерлоков.

Ответ API «принято» показывается отдельно от подтверждения по новому снимку телеметрии. Где критерий проверки не описан, панель прямо пишет, что автоматическое подтверждение не определено. При потере связи или отсутствии эффекта команда автоматически не повторяется. Журнал действий доступен на вкладке «Команды» и в JSONL-файле.

Команды доступны при активной роли `team` и свежей телеметрии. В гостевом режиме, при обрыве или устаревших данных отправка блокируется. Повторная отправка одного запроса с тем же токеном не создаёт второе действие. Запросы данных (например, список файлов) используют то же соединение.

При проверке реализации команды оборудования исполнялись на тестовом сервере; для реального купола использован запрос списка файлов.

## Панель и журналы

Панель доступна только через loopback этого компьютера. Ключ хранится на Python-сервере и не передаётся в браузер. Видны этапы подключения, роль/команда, ping, показания устройств, JSON, поиск, журнал ошибок и входящие сообщения. При отсутствии данных показатели остаются пустыми. Старый снимок после отключения помечается как неактуальный.

В `logs` создаётся новый JSONL-файл на запуск. Он содержит диагностику, запросы и каталог; полная телеметрия каждые две секунды не записывается. Это журнал транспортного клиента, не полный журнал решений будущего агента.

Коды завершения консоли: 0 — успешная проверка или остановка; 1 — ошибка соединения/протокола; 2 — отказ авторизации или ошибка конфигурации.

## Установка на другой машине

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Заполните `.env` своим ключом и адресом. При передаче проекта другим людям используйте `.env.example`.

## Тесты

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Тестовые серверы работают только на `127.0.0.1` с искусственным ключом. Проверяются обычный обмен, другая библиотека сервера (websockets), гостевой режим, ответы в обратном порядке, частота запросов, зависшее рукопожатие/авторизация, HTTP-страница вместо API, пропавшая телеметрия, отмена подключения, отзыв сессии и настоящий запуск CLI отдельным процессом.

История диагностики: старый адрес `62.118.24.234:48765` 26 октября не отвечал на HTTP/WebSocket. После получения адреса `wss://janus-server.a.2na.am:443/` подключение, авторизация, каталог и поток телеметрии успешно проверены; текущий статус указан в начале документа.
